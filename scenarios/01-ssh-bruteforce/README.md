# SSH Brute-Force Detection Lab

## Overview

This scenario demonstrates a controlled **SSH brute-force attack simulation and detection workflow** using a virtualized Ubuntu server and Splunk Enterprise.

The objective is to simulate repeated failed SSH authentication attempts, collect the resulting authentication logs, forward them to Splunk, and analyze the activity using **Splunk Search Processing Language (SPL)**.

This scenario represents a simplified **Security Operations Center (SOC)** workflow:

```text
Attack Simulation
       ↓
Ubuntu SSH Server
       ↓
/var/log/auth.log
       ↓
Splunk Universal Forwarder
       ↓
TCP 9997
       ↓
Splunk Enterprise
       ↓
SPL Detection
       ↓
Security Investigation
```

## Objectives

- Simulate repeated failed SSH authentication attempts in a controlled lab environment.
- Understand how SSH authentication events are recorded in Linux logs.
- Configure Splunk Universal Forwarder to collect authentication logs.
- Forward Ubuntu logs to Splunk Enterprise.
- Search and analyze SSH authentication events using SPL.
- Extract source IP addresses from raw log data.
- Develop detection logic for repeated failed SSH authentication attempts.
- Demonstrate a basic SOC investigation workflow.


The Universal Forwarder monitors the authentication log and forwards new events to Splunk Enterprise.

## Network Configuration

The lab uses the VirtualBox **NAT networking mode**.

The Splunk Universal Forwarder is configured to forward logs to:

```text
192.168.1.6:9997
```

TCP port `9997` is used as the receiving port for forwarded Splunk data.

The network connectivity between the Ubuntu system and the Splunk receiving port was verified before configuring log forwarding.

## Attack Simulation

A controlled SSH authentication attack was simulated against the Ubuntu server.

Multiple incorrect passwords were submitted through SSH to generate failed authentication events.

The purpose of the simulation was not to compromise the system, but to generate realistic authentication telemetry for security monitoring and detection.

Example event generated by the simulation:

```text
Failed password for rangga15 from 10.0.2.2 port 50684 ssh2
```

The failed authentication event was recorded by the Ubuntu SSH service in:

```text
/var/log/auth.log
```

## Linux Authentication Logs

Ubuntu records SSH authentication activity in:

```text
/var/log/auth.log
```

The log contains information such as:

- Timestamp
- SSH service
- Authentication status
- Username
- Source IP address
- Source port
- Authentication protocol

Example:

```text
2026-08-25T13:15:40.047662+07:00 rangga15-VirtualBox sshd-session[4735]: Failed password for rangga15 from 10.0.2.2 port 50684 ssh2
```

This information provides the telemetry required to investigate suspicious SSH authentication activity.

## Log Collection with Splunk Universal Forwarder

Splunk Universal Forwarder 10.4.2 was installed on the Ubuntu system.

The Universal Forwarder was configured to monitor:

```text

```

The monitored log was assigned:

```text
index = main
sourcetype = linux_secure
```

The forwarder was configured to send the collected events to the Splunk Enterprise instance running on Windows:

```text

```

The resulting data flow is:

```text
│
```

## SPL Investigation

The first investigation query searches for failed SSH authentication events:

```spl
index=main sourcetype=linux_secure "Failed password"
```

This query returns authentication events containing the `Failed password` string.

The results can then be investigated to identify:

- Targeted username
- Source IP
- Number of failed attempts
- Authentication timestamps
- Potential attack patterns

## Source IP Extraction

The source IP address is extracted from the raw SSH log using the `rex` command:

```spl
index=main sourcetype=linux_secure "Failed password"
| rex "Failed password for \S+ from (?<src_ip>\d+\.\d+\.\d+\.\d+)"
```

The regular expression extracts the IP address following `from` and stores it in the field `src_ip`.

For example:

```text
Failed password for rangga15 from 10.0.2.2
```

becomes:

```text
src_ip = 10.0.2.2
```

## Brute-Force Detection Logic

A basic brute-force detection rule was developed based on repeated failed authentication attempts from the same source IP.

Detection threshold:

```text
5 or more failed SSH authentication attempts
from the same source IP
within a 5-minute window.
```

The SPL detection query is:

```spl
index=main sourcetype=linux_secure "Failed password" earliest=-5m
| rex "Failed password for \S+ from (?<src_ip>\d+\.\d+\.\d+\.\d+)"
| stats count by src_ip
| where count >= 5
```

### Detection Process

```text
Failed SSH Authentication
          ↓
Extract Source IP
          ↓
Group Events by Source IP
          ↓
Count Failed Attempts
          ↓
Count >= 5
          ↓
Potential SSH Brute Force
```

The `earliest=-5m` condition limits the investigation to events occurring within the previous five minutes.

## Investigation Result

During the initial attack simulation, multiple failed SSH authentication events were successfully collected.

Example:

```text
Source IP: 10.0.2.2
Target User: rangga15
Event: Failed password
```

Multiple events from the same source were observed in Splunk.

This demonstrates that repeated authentication failures can be centralized and investigated using a SIEM platform.

> Note: `10.0.2.2` represents the source address observed by the Ubuntu VM within the VirtualBox NAT environment. In a real production environment, the observed source IP would depend on the actual network architecture.

## Limitations

This scenario is performed entirely within a controlled virtualized environment.

The simulation does not represent a production enterprise network.

The source IP address observed in the logs is influenced by the VirtualBox NAT configuration.

The detection rule is intentionally simple and is designed for learning and demonstration purposes. Production detection would typically incorporate additional context such as:

- Successful authentication after multiple failures
- Multiple targeted usernames
- Geographic or network context
- Known malicious IP intelligence
- Account lockout events
- Authentication baselines
- Correlation with other security events
